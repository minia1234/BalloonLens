# 빠른 글자 인식 파이프라인

이미지 인식 속도 검토(P0–P2)를 구현한 기록입니다. 무엇을 바꿨는지, 어떻게 쟀는지, 무엇을 하지 않기로 했는지를 적었습니다.

측정은 합성 샘플(`samples\synthetic`과 `tools\make_synthetic.py` 방식으로 그린 페이지)과 RTX 4070 SUPER에서 했습니다. 번역은 실제 Claude 대신 호출당 3초가 걸리는 가짜 번역기를 썼습니다. **실제 만화 페이지의 글자 인식 시간과 실제 Claude 응답 시간은 이 숫자에 들어 있지 않습니다.** 그 숫자는 아래 "내 PC에서 재기"로 직접 확인합니다.

## 항목별 상태

| 우선순위 | 항목 | 상태 | 어디에 |
|---|---|---|---|
| P0 | 구간별 시간 측정 | 구현 | `metrics.jsonl`에 단계별 시간 기록, `balloonlens.metrics_report`, `balloonlens.ocr_profile` |
| P0 | OCR 끝나기 전에 번역 시작 | 구현. 긴 페이지에서만 켜짐 (아래 "번역 호출") | `jobs.py` `_read_balloons` |
| P0 | 화면에 보이는 부분 먼저 | 구현 | 확장 `visibleBand` → 도우미가 그 구간의 타일과 말풍선을 먼저 읽음 |
| P1 | 재시도 줄이기 | 같은 결과를 3.4배 빠르게 읽도록 묶음 처리. 재시도 횟수를 줄이는 변경은 하지 않음 | `ocr.py` `_verify_all` |
| P1 | Base64 제거 | 업로드는 제거. 응답의 정리 이미지는 그대로 (아래 "하지 않은 것") | `sw.js` `submitJob`, `server.py` |
| P1 | 예열 강화 | 기본으로 켜짐, 첫 추론까지 끝나야 "준비됨" | `__main__.py`, `ocr.py` `prime` |
| P2 | CRAFT 대체 검출기 | 비교하지 못함. 같은 모델의 FP16은 측정해서 기각 | 아래 "하지 않은 것" |
| P2 | OCR 추론 배치 | 일본어는 이전에 구현됨. 이번에 재시도 읽기와 영어를 묶음 처리 | `ocr.py` |

## 한 페이지가 처리되는 순서

```
확장: 이미지 받기 → 화면에 보이는 구간 계산 → [길이 4바이트 | 옵션 JSON | 이미지 바이트] 한 덩어리로 전송
도우미: 디코딩 → 편집·작품 기억 조회 → (OCR 잠금)
  타일별 검출 (보이는 타일부터)  →  말풍선 8개씩 읽기  →  의심 판독만 묶어서 다시 읽기
  └ 긴 페이지만: 읽는 동안 앞 8개를 먼저 번역 호출
말풍선 최종 번호 매기기 → 레이아웃·말풍선 분석 → 번역 마무리 → 결과
```

- 이미 읽은 페이지(OCR 캐시)는 잠금을 기다리지 않고, 번역 호출 한 번으로 보냅니다.
- 같은 이미지를 두 작업이 동시에 읽으면 OCR은 한 번만 합니다 (잠금 뒤 캐시를 다시 확인).
- 작업이 취소되면 그때까지 읽은 말풍선을 저장해 두고, 같은 페이지를 다시 요청한 작업이 이어서 읽습니다 (`ocr_resumed`).

## 업로드 프로토콜

확장은 이미지를 Base64로 바꾸지 않습니다. `POST /v1/jobs`의 본문이 한 덩어리입니다.

```
Content-Type: application/x-balloonlens-page
[4바이트 길이(빅엔디언)] [옵션 JSON] [이미지 바이트]
```

- 옵션 JSON은 최대 64,000바이트이고, 이미지는 25 MiB까지입니다. 길이가 맞지 않으면 `400 bad_page`입니다.
- 옵션에는 `visible: [위, 아래]`(이미지 높이에 대한 비율)가 들어갑니다. 화면 밖이거나 높이를 모르면 `null`입니다.
- 예전 형식(JSON 안의 Base64)과 이미지만 보내는 형식도 도우미가 계속 받습니다.

## 화면에 보이는 부분 먼저

- 긴 이미지는 겹치는 타일로 나뉩니다. 보이는 구간에 닿는 타일부터 검출하고, 그 안의 말풍선을 먼저 읽습니다.
- 말풍선 근처의 아직 검출하지 않은 타일이 남아 있으면 그 말풍선은 기다립니다 (옆 상자가 붙어서 합쳐질 수 있기 때문). 마지막에 전체를 다시 묶어 최종 결과를 만들므로, 결과는 한 번에 검출했을 때와 같습니다.
- 실제 엔진으로 확인한 첫 영역 준비 시간:

| 페이지 | 타일 | 한 번에 | 보이는 타일부터 |
|---|---|---|---|
| 1000×4000, 말풍선 24개 | 3 | 732 ms | 160–241 ms |
| 800×6000 웹툰, 말풍선 4개 | 6 | 571 ms | 88–142 ms |

## 번역 호출

번역 호출은 말풍선 수와 상관없이 호출마다 2.7초쯤이 먼저 듭니다. 그래서 페이지를 쪼개 여러 번 부르면 첫 줄은 빨라져도 끝나는 시간이 늘어납니다. 가짜 3초 번역기로 `tools\pipeline_bench.py --rest-s 0`(무조건 쪼개기)을 돌린 결과:

| 말풍선 | 첫 줄 | 끝나는 시간 |
|---|---|---|
| 24개 | 29% 빨라짐 | 36% 늘어남 |
| 36개 | 44% 빨라짐 | 18% 늘어남 |

그래서 정책은 이렇습니다.

- 도우미가 한 페이지에 보내는 번역 단계는 **최대 2번**입니다. 8개씩 계속 쪼개지 않습니다. (번역기가 긴 페이지를 안에서 나누는 것은 별개입니다.)
- 앞 8개를 먼저 보내는 것은 **나머지를 읽는 데 `PIPELINE_REST_S`(2.5초) 이상 걸릴 때만** 합니다. 나머지 시간은 먼저 읽은 말풍선의 읽기 속도로 어림합니다.
- 이 PC에서 합성 페이지 말풍선 48개(1000×8320, 16줄 × 3열)는 작업 생성부터 페이지를 다 읽기까지 2.6–2.8초쯤입니다. 첫 묶음 1.1초를 뺀 나머지 읽기는 1.5초쯤이라 쪼개지 않습니다. 실제 만화에서 재시도가 많거나 GPU가 느리면 쪼개집니다.

## 다시 읽기

- 의심스러운 판독은 두 가지 전처리(여백+대비, 이진화)로 다시 읽고 가장 좋은 것을 고릅니다. 이 선택 규칙은 그대로입니다.
- 달라진 것은 읽는 방법입니다. 의심스러운 말풍선을 하나씩 읽던 것을, 같은 전처리 단계끼리 모아 한 번에 읽습니다.
- 오검출 크롭 24개 중 7개가 의심스러웠던 경우: 하나씩 877 ms → 묶음 260 ms (재인식 12번으로 같음). 글자와 재인식 횟수는 24개 모두 같았습니다.
- 몇 개를 다시 읽었고 그중 몇 개가 고쳐졌는지 기록합니다 (`ocr_retry_spans`, `ocr_retry_fixed`, `ocr_retry_ms`). 이 비율이 낮으면 재시도 조건을 줄일 근거가 됩니다. 실제 만화 데이터 없이 조건을 줄이면 품질 근거가 없어서, 지금은 줄이지 않았습니다.

## 예열

- 도우미는 켜지면 곧바로 두 OCR 모델을 올리고 한 번씩 돌려 봅니다 (`--no-warmup`으로 끌 수 있음). 이 PC에서 약 15–25초이고 로그에 `OCR 모델 준비: N초`로 남습니다.
- `status.ocr_ready`는 모델을 올리는 것뿐 아니라 첫 추론까지 끝나야 참이 됩니다. 이전에는 첫 추론이 끝나기 전에도 "준비됨"이었습니다. 첫 추론이 실패해도 참으로 바뀌며, 그때 첫 페이지가 같은 오류를 받습니다. 실패를 화면에 따로 표시하지는 않습니다.
- 예열 중에 페이지가 오면 GPU 락 뒤에서 기다립니다. 페이지 읽기와 예열이 GPU를 동시에 쓰지 않습니다.

## 내 PC에서 재기

실제 만화 페이지로 직접 확인하는 방법입니다.

```powershell
cd helper
# 번역 없이 글자 인식만: 단계별 시간, 다시 읽기 비율
.venv\Scripts\python.exe -m balloonlens.ocr_profile ..\samples\real\page1.png ..\samples\real\page2.png --runs 3
.venv\Scripts\python.exe -m balloonlens.ocr_profile page.png --visible 0.6,0.9   # 화면 아래쪽이 보이는 경우

# 평소 쓴 기록에서: 어느 단계가 몇 초를 차지하는지
.venv\Scripts\python.exe -m balloonlens.metrics_report --last 50

# 쪼개는 쪽이 이득인지 (가짜 번역기, Claude 호출 없음)
cd ..
helper\.venv\Scripts\python.exe tools\pipeline_bench.py --rows 8 --rest-s 0
```

`metrics.jsonl`의 시간 항목 (모두 ms, 작업 생성부터 잰 것은 표시):

| 항목 | 뜻 |
|---|---|
| `queue_ms`, `gate_ms`, `decode_ms`, `memory_ms` | 큐 대기, 사용량 확인, 이미지 디코딩, 편집·작품 기억 조회 |
| `ocr_lock_wait_ms` | 다른 페이지가 읽히는 동안 기다린 시간 |
| `detect_ms` | 글자 상자 검출과 묶기 (타일 합계) |
| `recognize_ms` | 말풍선 읽기 (다시 읽기 포함) |
| `ocr_retry_ms`, `ocr_retries`, `ocr_retry_spans`, `ocr_retry_fixed` | 다시 읽은 시간, 재인식 횟수, 다시 읽은 말풍선 수, 그중 고쳐진 수 |
| `first_read_ms` ↑ | 첫 말풍선 묶음을 읽은 시점 |
| `first_step_ms` ↑ | 첫 번역 호출이 시작된 시점 |
| `first_result_ms` ↑ | 첫 번역문이 나온 시점 |
| `visible_read_ms` ↑ | 화면에 보이는 말풍선을 다 읽은 시점 |
| `ocr_done_ms` ↑ | 페이지를 다 읽은 시점 (번역은 아직 진행 중일 수 있음) |
| `layout_ms`, `present_ms` | 레이아웃 적용, 말풍선 분석(보통 0.2–0.3초) |
| `translate_wait_ms`, `translate_rest_ms` | 읽은 뒤 번역을 기다린 시간, 단계가 못 덮은 줄을 마저 번역한 시간 |
| `translate_ms` | 첫 번역 호출부터 끝까지 |
| `total_ms` | 작업 전체 |
| `tiles`, `boxes`, `groups`, `steps`, `ocr_resumed` | 타일 수, 상자 수, 묶음 수, 번역 호출 수, 취소된 작업에서 이어받은 말풍선 수 |

해석은 이렇게 합니다. `recognize_ms`가 가장 길면 글자 인식(Manga OCR), `detect_ms`가 가장 길면 검출(CRAFT)입니다. 둘이 작은데 `ocr_done_ms`가 크면 큐 대기, 락 대기, 디코딩, 작품 기억 같은 다른 구간입니다. `metrics_report`가 이 규칙으로 진단 문장을 만들어 줍니다.

## 하지 않은 것과 이유

- **검출기를 FP16으로 돌리기**: 같은 박스가 나왔지만 빨라지지 않았습니다 (258 ms → 282 ms, 샘플 4장 모두 박스 좌표 차이 0). 검출 한 번에서 CPU 전처리·후처리가 40%쯤이고, 모델 부분도 정밀도를 낮춘다고 줄지 않았습니다.
- **다른 검출기(PP-OCRv5, Comic Text Detector) 비교**: 이 PC에는 설치돼 있지 않고, 비교하려면 패키지와 모델 파일을 내려받아야 해서 하지 않았습니다. 검출은 타일당 0.1–0.25초쯤이고, 긴 웹툰(6타일)에서 검출 전체가 0.5–1.5초입니다. 검출기를 바꿔 얻을 수 있는 시간은 이 범위 안입니다. 비교는 `ocr_profile`의 "detect" 열로 같은 이미지에서 해야 합니다 (속도와 누락률을 같이).
- **응답의 정리 이미지(`cleanup`)의 Base64 제거**: 24개 말풍선 페이지에서 34 KiB이고 최종 결과에만 한 번 실립니다 (원본 이미지 174 KiB). 확장 서비스 워커와 페이지 사이 메시지는 JSON만 전달해서 바이너리를 그대로 넘길 수 없고, 토큰이 든 주소를 페이지 DOM에 넣으면 페이지 스크립트가 토큰을 읽을 수 있습니다.
- **영어 인식 묶음 처리의 큰 효과**: 같은 글자가 나오지만 이득은 9–17%(말풍선 4개에서 23–37 ms)입니다. 인식기를 한 번 부르는 비용만 줄고 GPU 배치는 아닙니다. EasyOCR의 `batch_size`는 기본값 1 그대로 둡니다. 키우면 같은 묶음 안의 다른 상자 때문에 패딩이 달라져 결과가 바뀔 수 있는데, 이번에는 확인하지 않았습니다.
- **재시도 조건 줄이기**: 위 "다시 읽기" 참고.

## 열린 항목

- 실제 만화 페이지로 `ocr_profile`과 `metrics_report`를 돌려 보기. 특히 `ocr_retry_fixed / ocr_retry_spans`.
- 말풍선 분석(`present_ms`)은 번역 호출과 겹치지 않고 번역이 끝난 뒤에 돕니다. 이 겹치기는 `2026-10-13-latency-overlap.md`의 3번 항목에서 다룹니다.
